# QA — איך מונעים שבאג יגיע ללקוח

נכתב 19.9.2026 אחרי שבוע שבו כל יום התגלה באג בפרודקשן דרך לקוח או דרך הסוכן היומי.
המטרה: כל שינוי עובר את אותן בדיקות לפני שהוא מתמזג, וכל באג שנמצא הופך לבדיקה שלא תיתן לו לחזור.

## שלוש שכבות

| שכבה | מה בודקת | מתי רצה | איפה |
|---|---|---|---|
| **יחידה** | חישובי CRM (BMBY/Zoho/Salesforce), טווחי מודעות, raw-store, שומר תבנית ההרשאה | כל PR, כל push ל-main | `npm run qa` · `scripts/tests/*.smoke.mjs` |
| **build** | `next build` מצליח עם משתני הסביבה הציבוריים | כל PR | GitHub Actions `QA / next build` |
| **E2E (דפדפן)** | מה שלקוח רואה: כניסה, כל פרויקט נפתח, טאבים, רענון חוזר, בלי שגיאות JS ובלי 5xx | אחרי כל preview של Vercel, כל בוקר 08:30 מול פרודקשן, וידנית | `e2e/*.spec.mjs` · `npm run test:e2e` |

בנוסף, מה שכבר קיים ולא משתנה: שומר הקרונים (`/api/cron/health`) והסוכן היומי (`/api/v1/health` + אימות דיוק) —
הם מגלים תקלות **אחרי** הפריסה. שלוש השכבות למעלה אמורות לתפוס **לפני**.

## הכללים

1. **לא ממזגים PR אדום.** ב-GitHub: Settings → Branches → Branch protection ל-`main` → Require status checks:
   `בדיקות יחידה + שומר הרשאות`, `next build`.
2. **כל באג = בדיקה.** לפני שמתקנים, כותבים בדיקה שנכשלת; אחרי התיקון היא עוברת. הבדיקה נשארת עם תאריך ותיאור
   קצר (ראו ראש `e2e/client.spec.mjs`).
3. **הלקוח בודק בטלפון** — לכן ה-E2E רץ גם בפרופיל מובייל (Pixel 7), לא רק בדסקטופ.
4. **מסך "טוען..." בלי סוף הוא כשל**, גם אם אין שגיאה. כל בדיקת E2E מחכה שהספינר ייעלם תוך 20–30 שניות.

## הגדרה חד-פעמית (ויטלי)

1. **משתמש QA** עם גישת לקוח לכל הפרויקטים: `qa@vitas.co.il` — נוצר 19.9.2026 (משתמש Auth + 8 שורות
   `client_access`). הסיסמה נשמרת רק ב-GitHub Secrets. לאפס סיסמה: מסך הכניסה → "שלחו לי קישור כניסה" (המייל
   צריך תיבה קיימת) או `auth.users` ב-Supabase. לא להשתמש במשתמש אדמין אמיתי.
2. **GitHub → Settings → Secrets and variables → Actions:**
   - Variables: `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY` (אותם ערכים כמו ב-Vercel; ציבוריים).
   - Secrets: `QA_CLIENT_EMAIL`, `QA_CLIENT_PASSWORD`.
   - Secret: `VERCEL_AUTOMATION_BYPASS_SECRET` — Vercel → Project → Settings → Deployment Protection →
     Protection Bypass for Automation → Generate. בלעדיו ה-E2E לא יכול להיכנס ל-preview (מוגן ב-SSO).
3. **Branch protection** כמו בכלל 1.

## הרצה מקומית

```
npm run qa                    # יחידה + שומר הרשאות (שניות)
npm run test:e2e:public       # רק מסך הכניסה, בלי פרטי כניסה
QA_CLIENT_EMAIL=qa@vitas.co.il QA_CLIENT_PASSWORD=... npm run test:e2e
QA_BASE_URL=http://localhost:3000 npm run test:e2e     # מול שרת הפיתוח
npx playwright show-report    # דוח עם צילומי מסך ו-trace לכל כישלון
```

בפעם הראשונה: `npx playwright install chromium`.

## מה הבדיקות כבר מצאו

- **19.9 (הריצה הראשונה עם משתמש QA) — באג חמור אצל כל הלקוחות:** בטעינת פרויקט נבחרה "השורה הראשונה"
  מהאינדקס, שממוין לפי מפתח תקופה יורד. הקרון כותב מראש גם את הרבעון הבא (`2026-10-01_2026-12-31`, קיים מ-6.6),
  והמפתח הזה גדול מכל מפתח של ספטמבר — ולכן כל לקוח נחת על **תקופה עתידית וראה אפסים בכל הכרטיסים**, בזמן
  שהתגית הציגה "חודש שעבר". נמצא כי הבדיקה בודקת שיש ספרה שאינה 0 בכרטיסים. תוקן ב-`pickDefaultMonth`
  (`app/admin/page.js`) + בדיקת רגרסיה: אף בקשת נתונים לא מתחילה אחרי היום.

- **19.9 (הריצה הראשונה של ה-E2E):** באחת מ-6 טעינות של `/client`, קובץ JS אחד (`_next/static/chunks/...`) חזר עם
  502. התוצאה: העמוד הסטטי נשאר על "טוען..." לנצח — אין hydration, אין הודעה, אין כפתור. זה בדיוק מה שלקוח רואה
  ברשת סלולרית רעועה. תיקון מוצע: סקריפט קטן בעמוד שמציג "משהו השתבש — טען מחדש" אם ה-hydration לא קרה תוך 15 שניות.

## מה עוד לא מכוסה (הבא בתור)

- **ספינר סטטי בלי מוצא** (הממצא למעלה): כפתור רענון אחרי 15 שניות ללא hydration ב-`/client` וב-`/admin`.

- **אימות דיוק אוטומטי ב-CI**: `/api/reports/range?compare=1` ליום סגור לכל פרויקט BMBY — היום זה רץ רק
  בסוכן היומי. אפשר להוסיף כבדיקת E2E עם טוקן ניטור.
- **צד האדמין**: הענקת גישה, משיכה חיה, ייצוא — דורש משתמש אדמין ל-QA ובידוד מפרודקשן.
- **קרונים**: בדיקת חוזה ל-`prefetch-daily` / `prefetch-crm` (זמן ריצה < 280s, heartbeat נכתב) — היום מתגלה
  רק דרך השומר. אפשר להריץ אותם מול preview עם `CRON_SECRET` ולבדוק את גוף התשובה.
- **Visual regression** לעיצוב המחודש (ענף `redesign`): צילומי מסך של כל מסך מול baseline. נכניס כשהעיצוב יתייצב.
